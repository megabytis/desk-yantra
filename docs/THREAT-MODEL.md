# Threat model — initial review, 2026-11-20

Author: OpenAI Codex (GPT-6-sol). This is an implementation inventory and risk assessment, not an independent security review or certification. The current deployment target is one trusted Linux user on a trusted, local Arch/Hyprland machine. The browser, app and companion bind to loopback. Anyone who controls that Linux account or its Docker socket can bypass this product's boundaries. Untrusted users and internet exposure are outside the supported target.

| Boundary | Untrusted input and authority | Current control | Residual risk and required evidence |
| --- | --- | --- | --- |
| Browser → app | Local pages, extensions, HTTP requests, pairing token | Loopback binding, Host/Origin checks, HttpOnly SameSite cookie, CSRF header, request limit, logout/rotation | A hostile local process can reach loopback; token theft or browser compromise defeats pairing. Audit proxy headers, malformed bodies, token rotation races and rate limits. |
| App → companion | Authenticated requests on separate loopback port | Bearer token plus Origin rejection; grant and approval checks in companion | Same-account process can read local token; no OS-level peer identity. Token rotation and concurrent request behavior need stress tests. |
| Worker → companion | Model-selected tool arguments | Registered focused tools, run/profile/grant intersection, exact one-use approvals, execution-time checks | Prompt injection can propose harmful commands or submissions within a grant; approval quality and race boundaries need adversarial review. |
| Worker → model | Task text, prior events, tool results, approved screenshots | Connection-scoped credentials; image forwarded only for known vision capability after approval | Hosted endpoints receive task data. Binary/artifact content has no guaranteed redaction; provider trust and retention must be explained in UI. |
| Sandbox → host / Docker | Agent commands, web browser, downloaded files | Unprivileged container, dropped caps, resource limits, optional read-only share | Docker daemon access is effectively host root; sandbox retains network egress and persistent writable state. Expert isolation review, image pinning, quotas and egress policy remain. |
| Browser page → agent | Page text, scripts and downloads | Browser actions route through companion; navigation/interactions need approval | Page instructions can manipulate model decisions. External submissions, domain policy and data exfiltration controls remain open. |
| Artifact → user | Generated files, captures, downloaded content | Authenticated download and run metadata; file count/size limits | Files may contain executable payloads, secrets or malicious content. Binary redaction, preview safety, retention and provenance need verification. |
| Host files and shell | User-granted workspace, account-wide shell | Scoped file descriptors reject traversal, links and special files; shell requires exact approval | Shell is account-wide. A model can still ask for a dangerous command; approval review is the last barrier. Race and crash tests remain. |

Security invariants: untrusted content never grants authority; the companion checks the current grant at effect time; approvals are single use and bound to exact action/run; stop and revocation prevent new effects and terminate known processes; uncertain effects after interruption require review before fresh work. Existing tests cover portions of these invariants, but concurrency, reboot, Docker escape assumptions and independent review are release blockers.

Priority next checks: concurrent revoke versus file write/process launch; stop during approval; duplicate approval requests; worker restart with surviving command; hostile Origin/Host and malformed request variants; prompt injection from web content; artifact download content and browser preview handling. Each test should assert the real effect or absence of effect, not only an HTTP response.
